# Employee QR Passes

Сайт для учёта сотрудников и договоров, выпуска QR-пропусков и печати PDF A4.

## Короткий план

1. Создать отдельный публичный репозиторий `employee-qr-passes`.
2. Настроить статический сайт GitHub Pages через Actions.
3. Создать отдельный проект Supabase в организации владельца.
4. Применить миграцию из `supabase/migrations`.
5. Внести URL проекта и publishable key в `assets/js/config.js`.
6. Создать профили Auth для администратора и охраны.
7. Администратору вести сотрудников, фото, договоры и пропуска.
8. Охране сканировать QR и проверять только минимальные сведения.
9. Генерировать QR со случайным токеном без персональных данных.
10. Перевыпуск токена немедленно отключает старый QR.
11. Печатать один пропуск или пакет до четырёх пропусков на листе A4.
12. Просматривать журнал проверок с фильтрами.
13. Проверить права доступа и адаптивность перед вводом в работу.

## Возможности

- Чистый HTML/CSS/ES modules, адаптивный интерфейс с русским и узбекским переводами.
- Supabase Auth, Postgres, приватные бакеты и RLS.
- База сотрудников и договоров, уведомление о скором окончании договора.
- Индивидуальный QR, печатный PDF A4 и проверка камерой.
- Журнал удачных и неудачных проверок.

## Допущения и ограничения

- Название репозитория по умолчанию: `employee-qr-passes`; владелец GitHub по доступной интеграции: `platform770uz-dev`.
- Название организации в пропуске задаётся в `assets/js/config.js`, по умолчанию — «Организация».
- Supabase и GitHub Pages являются независимыми сервисами. Для этого проекта ещё требуется отдельный Supabase project; создание было остановлено лимитом двух активных бесплатных проектов в организации. Существующие проекты не изменялись.
- Есть техническое противоречие в требованиях к фото: охране нужно видеть фото при проверке, но приватное хранилище одновременно разрешено только администратору. PostgreSQL RPC не умеет самостоятельно выпускать Supabase Storage signed URL. В этой реализации Storage разрешает охране только чтение фото сотрудника, которое только что проверено этим же пользователем, в течение 2 минут; договоры остаются недоступны охране. Подписанный URL выпускается через Storage API после проверки. Это узкое исключение необходимо для показа фото на странице проверки.
- Rate limit RPC применяется на пользователя Supabase Auth (10 вызовов за 5 минут). Для интернет-сервиса с большим числом попыток дополнительно включите защиту от ботов на прокси/CDN.
- Шрифты Noto Sans Regular и Bold включены в `assets/fonts/`; условия SIL OFL 1.1 лежат в `assets/fonts/OFL.txt`. Источник: [Noto Sans](https://github.com/notofonts/latin-greek-cyrillic).
- Входные поля проверяются в браузере и рендерятся как текст, однако валидация клиента не заменяет ограничения базы и RLS.
- Первый пароль пользователя задаётся владельцем через Supabase Auth Dashboard; пример создания SQL профиля ниже не создаёт Auth-пользователя и не задаёт ему пароль.

## Установка

### 1. Создать проект Supabase и применить миграцию

1. Создайте проект в выбранной организации и регионе рядом с пользователями (для Узбекистана разумный выбор — `eu-central-1`).
2. В SQL Editor примените файл `supabase/migrations/202610240001_employee_qr_passes.sql` целиком. Миграция создаёт таблицы, приватные бакеты, RLS и RPC `verify_pass`.
3. Включите Email/Password в Authentication → Sign In / Providers.
4. В Storage убедитесь, что бакеты `employee-photos` и `contracts` остаются приватными.

### 2. Создать первого администратора и охранника

Сначала создайте каждого пользователя в Supabase Dashboard → Authentication → Users → Add user. Скопируйте UUID и выполните запрос отдельно для каждого:

```sql
update public.profiles
set role = 'admin' -- укажите 'guard' для охранника
where id = 'UUID_ИЗ_AUTH_USERS';
```

Роль хранится только в `profiles`; пользователь не может менять свою роль через клиент.

### 3. Настроить фронтенд

Откройте `assets/js/config.js` и укажите Project URL, publishable (или legacy anon) key, GitHub username и название организации. В публичном клиенте нельзя указывать secret/service-role key.

### 4. Включить GitHub Pages

В репозитории откройте Settings → Pages → Build and deployment → Source: GitHub Actions. Workflow `.github/workflows/pages.yml` публикует корень `main` после push.

GitHub Pages URL: `https://<username>.github.io/employee-qr-passes/`. После первой публикации откройте URL и проверьте, что приложение грузится по HTTPS.

### 5. Шрифт для PDF

PDF генератор встраивает `NotoSans-Regular.ttf` и `NotoSans-Bold.ttf`. Поддержка кириллицы и узбекских символов `oʻ`, `gʻ`, `ʼ` проверяется во время подготовки документа.

### 6. Печать пропуска

Выберите сотрудника и режим печати: один крупный пропуск либо четыре пропуска на листе. Для пакетной печати отметьте сотрудников в списке. В диалоге печати браузера выберите A4, масштаб 100%, поля по умолчанию и отключите колонтитулы. Для PDF используйте кнопку «Скачать PDF».

## Страницы

- `index.html` — вход по email/паролю.
- `admin.html` — список, карточка сотрудника, договоры и PDF.
- `scan.html` — сканер камеры для охраны.
- `verify.html` — проверка токена с телефона.
- `log.html` — журнал сканирований для администратора.

## Проверка перед использованием

- Примените миграцию на отдельном проекте и создайте две роли.
- Проверьте `verify_pass` как guard и убедитесь, что прямой `select` из `contracts` и `employees` отклоняется.
- Проверьте Storage: договор недоступен guard; фото доступно только после собственной недавней проверки.
- Проверьте перевыпуск QR и прекращение действия старой ссылки.
- Проверьте PDF на кириллице и `oʻ`, `gʻ`, `ʼ`; отсканируйте распечатанный QR.
- Откройте страницы на телефоне с шириной 360 px.

## Безопасность

В схеме нет паспортных данных или ИНН. Договоры хранятся в приватном бакете и доступны только admin через короткоживущую signed URL. В браузере используется только publishable/anon key. Токен QR — 256 случайных бит и сам по себе не раскрывает сведения о сотруднике.
